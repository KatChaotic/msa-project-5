### <a name="_qmphm5d6rvi3"></a>**Решение**

Существующее решение опирается на единственный узел сервера, который занимается обработкой файлов, их валидацией, преобразованием и загрузкой в базу данных. Это приводит к зависаниям всей системы а так же ошибках загрузки больших файлов, если время обработки начинает превышать стандартный Timeout ответа (обычно 60 секунд).

![](/out/task-4/results/tobe/tobe.png)

Предлагаемое архитектурное решение основывается на разделение ответственности валидации и загрузки файлов по разным узлам.

Первичную валидацию файла предлагается проводить на стороне API сервера, такую как например: формат файла, вес. При успешной валидации файл добавляется в хранилище Google Cloud Storage.

Обработка файла с преобразованием и загрузкой в базу данных происходит в отдельном Java приложении на основе SpringBatch фреймворка. Данный контейнер запускается на группу приходящих файлов по указанному расписанию. 
Т.к. на проекте используется Google Compute Engine и Google Cloud Storage, то возможна реализация автоматического запуска приложения на обработку файлов с помощью событийной модели без внедрения дополнительных инфраструктурных элементов. Это позволит гибко масштабироваться и подстраиваться под любую пиковую нагрузку.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

В качестве альтернативного решения можно было бы рассмотреть Apache AirFlow для построения пайплайна преобразования данных, что было бы полезно и удобно при появлении требований на разработку новых задач на преобразования.

Однако в текущей ситуации лучшим выбором является использование Spring Batch

- Команда имеет опыт разработки на Java, нет опыта на Python необходимый для AirFlow
- Обработка больших входных данных с помощью чанков из коробки, в отличии от AirFlow

**Недостатки, ограничения, риски**

При повышении нагрузки в 100 раз необходимо подумать о переходе на более подходящее решение для обработки больших данных, таких как Spark или Hadoop.

Текущее решение может быть затратным по ресурсам в пиковые нагрузки при настройке его через события Google Cloud Storage, поэтому необходимо ограничить максимально возможное количество инстансов приложения, которые могут быть запущены одновременно, чтобы быть готовыми к предсказуемым расходам.
